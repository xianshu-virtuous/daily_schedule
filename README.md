# daily_schedule（日程系统）

给 Bot 一份「自己的日程」，让它回答「你在做什么」时有个真实的答案，忙的时候也真的有个可以推脱的理由；
主人出现时，它会把时间让出来——而且让得像「我自己更想陪你」。

设计上刻意克制：**不强制场景、不强调、不补充**。日程只是背景，不是剧本。

## 安装

1. 把 `daily_schedule` 整个文件夹放到主程序的 `plugins/` 下（文件夹名保持 `daily_schedule`，与 `manifest.json` 的 `name` 一致）；
2. 重启 / 重新加载插件，框架会自动生成配置文件 `config/plugins/daily_schedule/config.toml`；
3. 打开 `plugin.enabled`（默认已开），按需调整 `[model]`（默认用主回复模型 `actor`）与 `[source]`（人设 / 记忆 / 互联网三层素材）；
4. 无需额外 Python 依赖（`python_dependencies` 为空）；记忆层与联网层都是「有就用、没有就跳过」，不装也能跑。

装好之后可以用 `/日程` 看状态、`/日程 重生成` 立刻生成一份今天的行程。

## 它做什么

- **预生成一天**：每天在 `schedule.prewarm_time` 之后自动生成当天日程（默认 00:05 起巡检，进程重启后也能自愈）
- **巡检看得见**：每 `schedule.check_interval_seconds`（默认 1800s，做测试可填 60）跑一次巡检兜底，每次只留一行短日志：
  `巡检 · 2026-09-21 日程正常（11 段）` / `巡检 · 10:30 未到预生成时刻（00:05）` / `巡检 · 2026-09-21 日程缺失或过期，开始生成`
- **启动就报备**：bot 启动加载插件后，日志里直接摊开今天在干什么——先一行概要，再一张表格
  （当前时段带 `▶` 并整行加粗）：

  ```
  [23:20:00] daily_schedule.service | INFO | 启动加载 · 2026-09-21 日程：4 段 ｜ 生成 23:09 ｜ 素材 persona,memory,internet ｜ 模型 task:actor
  [23:20:00] daily_schedule.service | INFO | ┌───────────────┬────────┬──────────────────────────────────────────────────────────────┐
  │ 时段          │ 忙     │ 在做什么                                                     │
  ├───────────────┼────────┼──────────────────────────────────────────────────────────────┤
  │   00:00-06:40 │ 空闲   │ 在宿舍床上蜷成一小团，抱着被子角睡得很沉，偶尔嘟囔一句听不…  │
  │   06:40-07:30 │ 有点忙 │ 刚爬起来，在镜子前梳头发，顺手把发尾的小结拆开重编           │
  │ ▶ 22:30-23:20 │ 空闲   │ 趴在床边看窗外的星，手指无意识地敲着床沿，像在数今晚有几颗…  │
  └───────────────┴────────┴──────────────────────────────────────────────────────────────┘
  ```

  表格宽约 90 列，`在做什么` 超长会在 60 列处截断；当天还没日程就说明原因并排一次生成，
  生成完再打一遍完整安排。让位中重启也会带上心声。

  这张表是**等启动画面收尾之后**才打的：Bot 初始化阶段用 Rich `Live` 画启动进度条，
  那期间往控制台写的日志会被进度画面盖掉（文件日志不受影响，但人眼在控制台看不到）。
  插件以「调度器已启动」（`Bot.start()` 里的事）作为信号，所以表格会落在
  `Bot 初始化成功` / `已触发 ON_START` 之后那一段，跟其它插件的日志排在一起。
- **轻量注入**：在 chatter 的 user prompt `extra` 板块追加一句「（你此刻正在：……）」，外加一行「这只是背景」的说明
- **不留强制痕迹**：不产生标题、不要求模型展开、不写「必须拒绝」这类规则；忙碌时给的只是「被搭话也可以说等会儿」的许可
- **主人到场让位**：权限系统判定为主人后，把日程时间让出来，措辞取自角色自己的心声池
- **落盘成日志**：生成结果写入 `data/json_storage/daily_schedule/`，既是运行记录，也是下次生成的连续性素材

## 素材顺序

按 **人设 → 记忆 → 互联网** 依次取材，任何一层缺失都只跳过该层，不影响生成：

| 层级 | 来源 | 缺失时的行为 |
| --- | --- | --- |
| 人设 | `config/core.toml` 的 `[personality]` | 人设不可用则放弃本次生成 |
| 记忆 | 记忆插件的服务（默认 `booku_memory:service:booku_memory`） | 服务不存在或检索失败即跳过 |
| 互联网 | 已注册的 MCP 搜索工具（自动探测，也可用签名指定） | 探测不到即跳过，不报错 |

互联网层是「有则用、无则跳过」：`source.search_tool_signature` 留空时自动匹配名字里带
`search` / `ddg` / `web` 等的 MCP 工具，匹配不到就安静地不用；本插件只依赖通用工具签名，不绑定任何特定工具。

## 模型调用（每天最多两次）

1. **人设类型判定**：区分「扮演已有角色」与「原创 OC（原创设定）」，结果按人设指纹缓存，人设不变就不再调用
2. **日程生成**：一次产出当天时段表、每段的「此刻在做什么」、忙碌等级、反应倾向，同时顺带产出
   - `yield_lines`：让位心声池（3-5 条，第一人称，语气是「是我更想陪你」）
   - `yesterday_summary`：前一天的一句话小结（写进日志）

默认使用主回复模型（`model.task_name = "actor"`），也可以用 `model.model_name` 直接点名某个模型。

让位与注入本身**不再额外调用模型**：让位文案从日程自带的心声池里挑，触发时选定的那句会在整段让位期间保持不变。

## 注入长什么样

```
（你此刻正在：在店里给一台旧收音机换电容，手上正忙，被搭话也可以说等会儿）
（手上占着，说话可以）
（这只是你此刻的状态背景。被问到时自然说起就行，不必主动提起，也不必展开描写。）
```

让位期间换成心声：

```
（你先说，我这边不急）
（这只是你此刻的状态背景。……）
```

注入目标模板由 `plugin.target_prompts` 控制，默认同时兼容 `default_chatter_user_prompt` 与
`neo_default_chatter_user_prompt`，只有当前实际启用的 chatter 会真正命中。与 prompt_injector、
booku_memory 等注入器通过换行累加共存，互不覆盖。

## 让位

- 身份校验走权限系统（`generate_person_id` + `get_user_permission_level`），默认要求 `owner` 级
- `scene.yield_scope`：`all`（私聊 + 群聊都算）/ `private`（只认私聊）
- `scene.yield_idle_minutes`：让位持续的静默时长（默认 30 分钟）；设为 `0` 表示持续到当天结束
- 让位期间的重复开口不会改措辞、也不会重复记日志

## 命令

命令级权限为 `owner`（主人的插件）。英文与中文别名均可：

```
/日程                    状态摘要（此刻在做什么）
/日程 查看   /status     状态摘要
/日程 全天   /today      列出今天全部时段
/日程 重生成 /regenerate 强制重新生成今天的日程（后台执行）
/日程 人设   /persona    查看人设类型判定结果
/日程 让位   /yield      手动让位（验证文案用）
/日程 收回   /unyield    结束让位
/日程 日志   /log        最近几天的生成记录
/日程 帮助   /help       帮助
```

## 配置

配置文件：`config/plugins/daily_schedule/config.toml`（首次加载时按字段说明自动生成）

| 节 | 关键项 | 说明 |
| --- | --- | --- |
| `[plugin]` | `enabled` / `debug_log` / `target_prompts` | 总开关、调试日志、注入目标模板 |
| `[model]` | `task_name` / `model_name` / `temperature` / `max_tokens` | 生成所用模型与采样参数 |
| `[source]` | `use_persona` / `use_memory` / `use_internet` / `search_query` | 三层素材开关与检索词模板 |
| `[schedule]` | `prewarm_time` / `check_interval_seconds` / `generate_on_demand` / `refresh_if_older_hours` / `min_entries` / `max_entries` | 预生成时刻、巡检间隔（秒，最小 30）、按需补生成、过期刷新与条目区间 |
| `[scene]` | `enabled` / `template` / `busy_suffix` / `busy_min_level` / `hint_template` / `note` / `fallback` | 注入文本模板与忙碌许可阈值 |
| `[scene]` | `yield_enabled` / `yield_min_level` / `yield_scope` / `yield_idle_minutes` / `yield_template` | 让位开关、权限门槛、范围、时长与模板 |
| `[log]` | `enabled` | 是否写生成日志 |

全部关闭注入的方式：把 `plugin.enabled` 设为 `false`（插件不注册任何组件，等同整体下线），
或只关 `scene.enabled` 保留生成与日志。

## 存储

命名空间 `daily_schedule`，路径 `data/json_storage/daily_schedule/`：

- `schedule-YYYY-MM-DD.json`：某天的日程（条目、心声池、素材来源、模型标识）
- `log-YYYY-MM-DD.json`：某天的日志（生成记录 + 事件流，如让位）
- `persona-profile.json`：人设类型判定缓存（带人设指纹）
- `runtime-state.json`：让位与生成节流状态、最近一次失败原因

## 出问题时先看这几行日志

| 日志 | 含义 | 怎么办 |
| --- | --- | --- |
| `启动加载 · …` | 启动时查到了今天的日程 | 正常，紧跟着就是当天日程表格（当前时段带 `▶`） |
| `今天（X）还没有日程，将在 00:05 之后自动生成` | 启动时还没有日程 | 后面会跟一句排队/正在生成，生成完会再打一份 |
| `巡检 · X 日程正常（N 段）` | 巡检兜底跑过一次，一切正常 | 正常 |
| `日程生成失败：无法解析 JSON（N 字，内容：…）` | 模型没按格式返回 | 看括号里那段：结尾断在半句上就是被 `max_tokens` 截断，把 `model.max_tokens` 调大；是散文就换个更听话的模型或把 `model.model_name` 指到指定模型。完整原始返回留在 `data/json_storage/daily_schedule/raw-failure-last.json` |
| `日程生成失败：条目仅 N 条，低于下限` | 条目太少 | 把 `schedule.min_entries` 调小，或调大 `max_tokens` |
| `等 30s 仍没拿到日程服务，跳过启动日程报告` | 加载顺序异常或启动极慢 | 罕见；说明插件本身能用，只是这次没报备 |
| `人设判定失败，退回保守结果` | 人设判定那一步没解析出来 | 不影响生成，日程会按「原创 OC + 昵称」来做 |
| `模型调用失败: …` | 模型/网络层报错 | 按报错内容查模型配置 |
| 表格框线歪了 | 终端按字符宽度渲染，或窗口太窄折了行 | 表格按显示宽度（中文算两列）对齐，宽约 90 列；把终端拉宽到 100 列以上即可 |
| 文件里有 `启动加载 · …`，控制台却没有 | 报备打早了一点点，被启动进度条盖掉 | 1.0.0 起会等启动画面收尾再报；若仍看不到，看日志文件（控制台只是被覆盖，日志没丢） |

解析层本身已经比较宽容：代码围栏、前后散文、`//` 注释、尾逗号、全角引号、单引号、
JSON 前面带思考文字、甚至输出被 `max_tokens` 截断，都会尽量救回来（截断时至少保留写完的条目）。

想看完整的提示词与模型原始返回，把 `plugin.debug_log` 打开（DEBUG 级）。

## 维护者注意（四个踩过的坑）

1. **Service 不是单例**：`service_api.get_service()` 每次调用都会新建实例。
   跨调用者共享的状态只能放两处——类属性（进程内）或 `store`（落盘）。
   本插件的日程 / 日志 / 让位状态都在盘上，而「正在生成」闸门放在
   `ScheduleService._generating`（类属性）。放实例属性上等于没有闸门，
   同一天会被重复生成。
2. **`__init__.py` 不要 re-export 入口模块**：加载器是把入口文件当
   `daily_schedule.plugin` 直接执行的，那一刻包正在初始化中，
   再 `from .plugin import ...` 会循环导入并让整个插件加载失败
   （表现为 `cannot import name 'DailySchedulePlugin'`）。插件类从
   `plugin` 模块取用即可。
3. **画表格要自己算显示宽度**：框架日志先按 Rich markup 解析消息，再在终端里
   按列宽折行，所以中英混排必须按显示宽度补空格（中文两列，见 `table.py`），
   单元格里的 `[` 也要转义成 `\[`，否则会被当成样式标签吞掉。
   整行加粗只影响控制台——写进文件时框架会用 `Text.from_markup(...).plain` 把标记剥掉。
4. **启动期间的日志会被启动进度条盖掉**：Bot 初始化用 Rich `Live` 画进度条
   （`src/app/runtime/console_ui.py` 的 `startup_progress`），`Console.print` 并不与
   `Live` 协调，这期间打的日志会被每秒十几次的进度重绘覆盖——**文件日志照写，控制台看不见**。
   所以「启动后要给人看的东西」必须等启动画面收尾：本插件用「调度器已启动」
   （`Bot.start()` 里 `scheduler.start()` 之后）作为信号，并且超时就照打不误。
