# daily_schedule（日程系统）

给 Bot 一份「自己的日程」，让它回答「你在做什么」时有个真实的答案，忙的时候也真的有个可以推脱的理由；
主人出现时，它会把时间让出来——而且让得像「我自己更想陪你」。

设计上刻意克制：**不强制场景、不强调、不补充**。日程只是背景，不是剧本。

## 为什么不单独出：这是组合技

一个光会「排今天做什么」的日程插件，最后一定会退化成幻觉：模型不知道这段时间到底过没过、
自己又做了什么，于是只能在每轮对话里**现编**一句「我刚在看书」——编完就丢，下一轮换个新的，
前后对不上，主人一问就露馅。

所以这东西要三样合起来才对：

| 锚 | 来自 | 解决什么 |
| --- | --- | --- |
| **时间锚** | `time_sense`（同作者，可选依赖） | 这段离线**真的**有多长、从几点到几点 |
| **框架锚** | 自己的日程表 | 那段时间**本来**安排的是什么 |
| **记忆锚** | 记忆插件（有则用，没有跳过） | 那段时间前后**真实**聊过什么 |

模型只负责把三者缝成一句话，而缝完的结果会**落盘成日记**（`diary-YYYY-MM-DD.json`），
下次生成日程时再把它当素材读回来——于是「我昨天做了什么」变成**有据可查的一件事**，
而不是每轮现编的台词。编出来的东西被记下来、下次以事实的身份参与生成，这一环就是闭环。

没有 `time_sense` 也能跑：它在 manifest 里**不是依赖**（`dependencies.plugins` 是空的），
靠运行时探测服务签名来发现——装了就自动打开离线生活（v1.1.1 起的检测机制），
没装就安静地不做事，不会因为「缺依赖」被框架剔除。

> 为什么专门强调这一点：框架对 `dependencies.plugins` 里找不到的插件是**静默剔除**
> （`loader.py::_prune_unloadable_plugins`），`dependencies_required: false` 救不回来。
> 「有它更好、没有也能跑」的东西**一律不许写进依赖**——v1.1.1 及更早的版本写错过，
> 结果是没装 `time_sense` 的用户装完日程系统等于没装。

## 安装

1. 把 `daily_schedule` 整个文件夹放到主程序的 `plugins/` 下（文件夹名保持 `daily_schedule`，与 `manifest.json` 的 `name` 一致）；
2. 重启 / 重新加载插件，框架会自动生成配置文件 `config/plugins/daily_schedule/config.toml`；
3. 打开 `plugin.enabled`（默认已开），按需调整 `[model]`（默认用主回复模型 `actor`）与 `[source]`（人设 / 记忆 / 互联网三层素材）；
4. 无需额外 Python 依赖（`python_dependencies` 为空）；记忆层与联网层都是「有就用、没有就跳过」，不装也能跑。

想让 Bot 拥有「离线生活」（重启后知道自己不在的时候过了多久、做了什么），装上同作者的
`time_sense` **就行，不用再改配置**——插件加载时会检测到它，并自动打开离线生活。
它是**可选依赖**：没装也不影响日程本身，只是离线生活那部分安静地不做事。
（可选依赖**不写进 manifest 的 `dependencies.plugins`**，否则缺它会被框架静默剔除；
本插件从 v1.2.0 起改成纯运行时探测。）

装好之后可以用 `/日程` 看状态、`/日程 重生成` 立刻生成一份今天的行程。

## 它做什么

- **预生成一天**：每天在 `schedule.prewarm_time` 之后自动生成当天日程（默认 00:05 起巡检，进程重启后也能自愈）
- **三层规划**：年程 → 月程 → 周程，每层围绕上一层生成（见下文），缺哪层补哪层
- **两种日程来源**（`schedule.mode`，详见下文「日程池」）：`pool`（默认）从日程池抽取，`daily` 每天让模型写一份
- **离线随机评估**：离线回来时对「这周 / 这月正在推进的事」掷一次骰（八成顺利、两成卡住），结果写进日记与计划
- **巡检看得见**：每 `schedule.check_interval_seconds`（默认 1800s，做测试可填 60）跑一次巡检兜底，每次只留一行短日志：
  `巡检 · 2026-09-21 日程正常（11 段）` / `巡检 · 10:30 未到预生成时刻（00:05）` / `巡检 · 2026-09-21 日程缺失或过期，开始生成`
- **启动就报备**：bot 启动加载插件后，日志里直接摊开今天在干什么——先一行概要，再一张表格
  （当前时段带 `▶` 并整行加粗）：

  ```
  [23:20:00] daily_schedule.service | INFO | 启动加载 · 2026-09-21 日程：4 段 ｜ 生成 23:09 ｜ 素材 persona,memory,internet ｜ 模型 task:actor
  [23:20:00] daily_schedule.service | INFO | ┌───────────────┬────────┬──────────────────────────────────────────────────────────────┐
  │ 时段          │ 忙     │ 在做什么                                                     │
  ├───────────────┼────────┼──────────────────────────────────────────────────────────────┤
  │   00:00-06:40 │ 空闲   │ 在宿舍床上蜷成一小团，抱着被子角睡得很沉，偶尔嘟囔一句听不…  │
  │   06:40-07:30 │ 有点忙 │ 刚爬起来，在镜子前梳头发，顺手把发尾的小结拆开重编           │
  │ ▶ 22:30-23:20 │ 空闲   │ 趴在床边看窗外的星，手指无意识地敲着床沿，像在数今晚有几颗…  │
  └───────────────┴────────┴──────────────────────────────────────────────────────────────┘
  ```

  表格宽约 90 列，`在做什么` 超长会在 60 列处截断；当天还没日程就说明原因并排一次生成，
  生成完再打一遍完整安排。让位中重启也会带上心声。

  这张表是**等启动画面收尾之后**才打的：Bot 初始化阶段用 Rich `Live` 画启动进度条，
  那期间往控制台写的日志会被进度画面盖掉（文件日志不受影响，但人眼在控制台看不到）。
  插件以「调度器已启动」（`Bot.start()` 里的事）作为信号，所以表格会落在
  `Bot 初始化成功` / `已触发 ON_START` 之后那一段，跟其它插件的日志排在一起。
- **双路注入**：主路把「（你此刻正在：……）」写进 chatter 的 **system reminder**
  （那套 `<system_reminder>` 标签，模仿 DFC 用 `with_reminder="actor"` 拾取的写法），
  兜底仍在 user prompt 的 `extra` 里追加一句——两条路内容一致，因为不是所有 chatter 都会拾取 reminder
- **防背书**：注入文本与模型提示词里都明说「这是背景，不是要你念出来的台词：不要复述原句、
  不要照搬措辞」。这条来自实测：V4.1 系模型会把注入进来的现成句子**整句搬进回复**
- **不留强制痕迹**：不产生标题、不要求模型展开、不写「必须拒绝」这类规则；忙碌时给的只是「被搭话也可以说等会儿」的许可
- **主人到场让位**：权限系统判定为主人后，把日程时间让出来，措辞取自角色自己的心声池；
  v1.2.0 起这份让位**只对「主人开口的那个会话」生效**（别的群照常看她的日常），
  换会话不会互相串味
- **写完还要被看见**：离线日记默认注入对话（`offline.inject_enabled = true`），
  不注入的话日记就只是躺在盘上的一段独白
- **落盘成日志**：生成结果写入 `data/json_storage/daily_schedule/`，既是运行记录，也是下次生成的连续性素材

## 省 token 的账（实测，不是估的）

拿真实数据量过（爱弥斯 2026-09-24 那份日程与日记）：每轮往 prompt 里塞的东西 ≈

| 内容 | 字数量级 | 占比 |
| --- | --- | --- |
| 场景行（`你此刻正在：…` + 忙碌后缀） | ~50 | 10% |
| 防背书 `note` | ~40 | 8% |
| **日记注入块** | **~406** | **82%** |
| 合计 | ~498 | |
| 双路重复（reminder 与 extra 各一份） | **~996** | |

按 120 请求/天算 ≈ **12 万字/天/副本**。默认配置下现在只剩：

| 优化 | 做法 | 省下 |
| --- | --- | --- |
| 日记不再每轮发 | `offline.inject_turns = 3`：每记完一次日记，只在之后 3 轮注入（计数器落盘） | ~406 字 × 其后所有轮次 |
| 同一段背景只付一遍 | `scene.channel = "reminder_first"`：reminder 写成功就不再写 extra；写失败自动退回 extra | ~498 字/轮-请求 |
| 闲时不写反应倾向 | `scene.hint_only_when_busy = true` | 忙时才有那一行 |

稳态 ≈ **50 字/轮-请求**（场景行 + note），日记只在离线后头几轮出现一次。

还想更省：

- 场景行本身已经是最小单位了；真要再压就缩短 `scene.template` 与 `scene.note`
  ——但 `note` 是防背书的保险，删了它省的是 token，赔的是人设；
- 生成侧：池子默认 5 次/周，`variants_per_slot=2` + `archetypes=2` + `weekend_archetypes=0` → 2 次/周；
- `model.max_tokens` **别乱调低**：思考模型会把预算吃光，省下的是"错误"不是"钱"（见 D13）；
- 真正的杠杆是**把生成与缝合指到便宜模型**：`model.model_name = "deepseek-v4-flash"`。
  插件不预设厂商（用户可能不用 DeepSeek），这一条得自己填。

## 三层规划：年程 → 月程 → 周程

日程要同时满足两件相反的事：**稳定**（她前后一致、像同一个人）和**新鲜**（不会连着三天做同一件事）。
把两者压在一层里就会变成早期那版：每天重写一遍，结果既不稳定（前言不搭后语）又没变化（抄昨天骨架换词）。

所以按「越上层越稳、越下层越活」排成四层，**每层围绕上一层生成**：

| 层 | 它回答什么 | 变化程度 | 默认模式 |
| --- | --- | --- | --- |
| **年程** | 这一年准备怎么过（大方向） | 最低 | pool |
| **月程** | 这个月的目标；**分忙碌 / 休息**（学生：学期月 vs 寒暑假月） | 低 | pool |
| **周程** | 这周该干什么（把月目标落到周内节奏，可标「周三偏重」） | 中 | pool |
| **日程** | 每天每段具体做什么；**随机评估的判落点**；结合记忆与日记 | 最高 | pool |

每层都有两种模式，语义统一：

- **`pool`（默认）**：编几套**型**（"这类时期通常怎么过"的模板），到期抽一套，
  再用上层目标**规则化填充**——抽取与填充都不调模型，于是"编一次用很久"；
- **`direct`**：到期现场生成一份（一层一次调用，更贴合当下）。

几个刻意的设计：

- **有效期跟自然边界走，不设天数**：周程周一作废、月程月初作废、年程元旦作废——
  免得「这周的安排」用到下周三还挂着。
- **断链不致命**：缺哪层补哪层；某一层没生成出来，下层照常生成（没有月程也能有周程，
  没有周程也能有日程），只是少了点依据。
- **周程真的约束日程**（不是只当背景）：日型带 `tags`（如「训练」「外出」），
  周程说「今天偏重出门办事」，抽取时就优先挑标签对得上的日型——**零调用的字符串匹配**。
- **事实优先**：计划是期望，日记与日程是事实。下一轮生成上层规划时，实际发生过的日程、
  日记、以及随机评估的结果都会作为材料喂回去纠正计划。没有这条，三层会互相背书
  （计划写在那儿，模型就照着念）。
- **规划默认不进对话**（`plan.inject_in_chat = false`）：它只在生成侧起作用，不占每轮 token；
  想让她直接聊起「这周在忙什么」再打开。

```
[规划] 已生成月程 2026-09：「开学月」（busy，2 条推进项，模式 pool）
[规划] 已生成周程 2026-W40：「推进周」（busy，2 条推进项，模式 pool）
[抽取] 已从池子抽取 2026-09-30 日程：日型 workday-out（13 段）   ← 周程说今天出门，命中「外出」标签
[评估] 随机评估：把课程论文写完：顺利；去训练场练刀：卡住了      ← 离线回来时的掷骰
```

命令：`/日程 规划` 看三层计划（含型池与到期），`/日程 重规划` 强制重生成（后台）。

## 离线随机评估（八成顺利 / 两成卡住）

离线回来结算时，对**周程与月程里正在推进的事**掷一次骰（`offline.roll_success_rate`，默认 0.8）：

- **顺利（8 成）**：日记写成一笔踏实或高兴的记录；
- **不顺利（2 成）**：写成"卡住了"，带一点低落或不甘心。

三条硬约束：

1. **结果落盘**（写进计划文件的 `progress`，也留档在日记 entry 的 `outcomes` 里），
   同一条只评估一次——否则重启一次心情就换一次，人设自相矛盾；
2. **每天最多评估一次**（`runtime-state.last_roll_date`），一天里多次重启不会让情绪来回横跳；
3. **缝进日记时两种结果要用两种语气写**（提示词里明说），否则"顺利/卡住"会被写成同一句话。

`/日程 日记` 会连带显示「这次评估：……」，能一眼看出那天她到底被判定成什么。

## 日程池（`schedule.mode = "pool"`，默认）

**问题**：每天让模型重写一遍「今天」，它会把回喂给它的昨天当成模板来换词。同一台 bot 连续三天的日程，
13 段逐段对应——连「海豹涂鸦」「鞋带解了又系」「擦药膏」「看手机等消息」这些细节都在重复。
单调不是「每天只生成一次」的锅，是「把昨天回喂给它、又要求它接得上」的锅。

**做法**：把「变化」和「连续」拆开。

| | 现在（daily） | 池子（pool，默认） |
| --- | --- | --- |
| 变化来自 | 模型每天重写（结果：抄昨天） | **日型轮换 + 时段变体抽取**（不调模型） |
| 连续性来自 | 回喂昨天日程，要求「接得上」 | 日记 + 前几天**实际过过的**日程（事实，不是模板） |
| 模型调用 | ≈ 每天 1 次（30 次/月） | 每周刷一次池：工作日 3 套 + 周末 2 套 = 5 次（≈21 次/月），每日抽取 0 次 |

三层结构：**日型（一整套自洽的骨架）→ 时段 → 变体**。

```
工作日日型 3 套 + 休息日日型 2 套        ← 每 pool.refresh_days（默认 7）天重编一次
   └─ 每套 6-14 段，覆盖 00:00-23:59
        └─ 每段 2-4 个变体（同一场地/主题下换动作、换细节，不许只换措辞）
每天：按星期取桶 → 挑「最久没用过」的日型 → 每段确定性抽一个变体 → 落盘成 schedule-YYYY-MM-DD.json
```

几个刻意的设计：

- **变体必须属于同一个日型**：只按时段乱抽会出现「上午在图书馆、下午在床上、中间没有移动过程」的混乱；
  同一个日型内，场地与大主题固定，变体只换具体动作。
- **抽取是确定性的**：种子来自 `hashlib(日期 + 日型 + 时段)`（不用内置 `hash()`，它带进程随机化），
  所以「今天她在做什么」一整天前后一致、进程重启也不变；同时会避开昨天同一时段的同一句话。
- **工作日 / 周末分桶**：否则周末还在上课练刀，一眼假。`pool.weekend_archetypes = 0` 表示不区分（不推荐）。
- **每天抽的日型避开最近用过的**：优先用「最久没用过」的，全用过时用最久远的那套，同久用日期打破平局。
- **「重生成」是真的换一套**：池子模式下 `/日程 重生成` 会避开今天已抽过的日型。
- **注入没变**：抽出来的就是「今天的日程」，仍然写进 `schedule-YYYY-MM-DD.json`，所以日记锚点、
  让位心声、`/日程` 命令、注入逻辑都不用改——它们读的还是「今日实际」。

### 写坏率怎么压（池子一次写坏就是坏一整周）

1. **一次只编一个日型**（输出小、不容易被截断），失败可单独重试，并把**具体问题反馈**给模型（"第 3 段有空档"）；
2. 每个日型过一遍**机械校验**：覆盖 00:00-23:59、首尾相接无空档/重叠、段数与变体数达标、
   同段变体不许完全重复、不许出现「日程/让位/系统」这类词——不合格**不进池**；
3. **增量落盘**到 `pool-staging`：编好一个存一个，重启接着编，不必从头再来；
4. **只有整池达标才替换** `pool-current`（工作日日型 ≥ `pool.min_archetypes`）：
   刷池失败时旧池子原封不动，只是少几个日型；
5. 池子不可用（没编好 / 编坏了 / 过期 / 换人设）→ 按 `pool.fallback_to_daily`（默认开）**回退 daily**
   现生成一份，绝不让今天没日程；
6. 换人设（指纹变）自动作废整池，不会拿着旧角色的日子套新角色。

### 什么时候你会看到它

```
[启动] 巡检 · 2026-09-29 日程正常（13 段）                 ← 池子模式下的日常一行
[刷池] 日型已编好：workday-0 训练日（13 段，变体 3-3 个）    ← 编一个存一个
[刷池] 池子已刷新：2026-09-29-a1b2c3d4（5 个日型，6 条心声，有效期至 10-06 00:12）
[抽取] 已从池子抽取 2026-09-29 日程：日型 workday-2（13 段）  ← 每天这一行不花模型调用
[回退] 池子不可用，回退到 daily 模式生成今天                  ← 首次安装或池子坏掉时
```

命令：`/日程 池` 看池子（日型、变体数、有效期、最近失败），`/日程 刷池` 手动重编（后台，几分钟）。


## 素材顺序

按 **人设 → 记忆 → 互联网** 依次取材，任何一层缺失都只跳过该层，不影响生成：

| 层级 | 来源 | 缺失时的行为 |
| --- | --- | --- |
| 人设 | `config/core.toml` 的 `[personality]` | 人设不可用则放弃本次生成 |
| 记忆 | 记忆插件的服务（默认 `booku_memory:service:booku_memory`） | 服务不存在或检索失败即跳过 |
| 互联网 | 已注册的 MCP 搜索工具（自动探测，也可用签名指定） | 探测不到即跳过，不报错 |

互联网层是「有则用、无则跳过」：`source.search_tool_signature` 留空时自动匹配名字里带
`search` / `ddg` / `web` 等的 MCP 工具，匹配不到就安静地不用；本插件只依赖通用工具签名，不绑定任何特定工具。

## 模型调用（池子模式下每周几次）

`pool` 模式（默认）：

1. **编池子**（每 `pool.refresh_days` 天一次）：**每个日型一次调用**
   —— 默认工作日 3 套 + 休息日 2 套 = 5 次/周 ≈ 21 次/月；编好一个存一个，失败可单独重试；
2. **人设类型判定**：结果按人设指纹缓存，人设不变就不再调用（刷池时最多一次）；
3. **每日抽取不调模型**：变化来自轮换与变体，不来自现编。

`daily` 模式（`schedule.mode = "daily"`）：

1. **人设类型判定**：同上，按指纹缓存；
2. **日程生成**：每天一次，一次产出当天时段表、每段的「此刻在做什么」、忙碌等级、反应倾向，同时顺带产出
   - `yield_lines`：让位心声池（3-5 条，第一人称，语气是「是我更想陪你」）
   - `yesterday_summary`：前一天的一句话小结（写进日志）

  这一模式已加上「前几天的记录是**已用过的骨架**，今天的场地与事件至少一半要和它们不同」的约束
  （见 `_GENERATE_SYSTEM` 第 8 条与 `_history_block` 的措辞）——实测能减一部分重复，
  但结构上仍不如池子：它每天都得现场编，重复度取决于模型那天听不听话。

默认使用主回复模型（`model.task_name = "actor"`），也可以用 `model.model_name` 直接点名某个模型。

**`model.max_tokens` 默认 4000，别照搬旧版的 2000 之后又去怪模型写得短**：
`actor` 任务在不少实例里是**轮询池**（可能混着思考模型），思考链会先吃掉这份预算，
给低了就表现为「空返回」或 JSON 被截断——那不是它写得少，是正文压根没输出。

让位与注入本身**不再额外调用模型**：让位文案从日程自带的心声池里挑，触发时选定的那句会在整段让位期间保持不变。

## 注入长什么样

```
（你此刻正在：在店里给一台旧收音机换电容，手上正忙，被搭话也可以说等会儿）
（手上占着，说话可以）
（以上只是你此刻的状态背景，不是要你念出来的台词：不要复述这句话本身、不要照搬里面的措辞、
不要主动提起或展开描写；被问到时用你自己的话说个大概就行。）
```

让位期间（只在触发让位的那个会话里）：

```
（你此刻正在：在店里给一台旧收音机换电容）
（以上只是你此刻的状态背景，……）
（你先说，我这边不急）
```

### 两条注入路径 × 两个桶

| 路径 | 写入位置 | 谁拾取 | 开关 |
| --- | --- | --- | --- |
| **system reminder（主）** | 日程行 → `prompt_api.add_system_reminder(bucket="actor", name="daily_schedule_scene", …)`；让位行 → `prompt_api.add_stream_reminder(stream_id, …)`。都是 `dynamic` + 同名覆盖写 | DFC / NDFC 建请求时按 `with_reminder="actor"` 自动拾取全局 + 当前流私有 bucket，包成 `<system_reminder>…</system_reminder>` | `scene.reminder_enabled` / `reminder_bucket` / `reminder_name` |
| **extra（兜底）** | `on_prompt_build` 事件里的 `values["extra"]` | 所有 chatter 的 user prompt 模板 | `scene.enabled` + `plugin.target_prompts` |

为什么要绕到 reminder：带 `<system_reminder>` 标签的文本在模型眼里是**系统级元指令**，
而不是「一段等着被念出来的旁白」——这正是背景不再被背书的关键。`dynamic` + 同名覆盖
意味着每轮读到的都是**当下这一刻**的场景，不会残留上一段的。

写 reminder 失败只会降级成「这轮退回 extra 注入」，不影响对话。

**为什么日程行进全局桶、让位行进流私有桶**：日程是 Bot 自己的状态，对所有对话者一致；
而让位是「主人在**这个**会话开口」引起的——写进全局桶的话，主人在 A 群说句话，
B 群的场景行也会变成「我更想听你说」。所以：

- `values` 里其实**有** `stream_id`（`on_prompt_build` 的参数里没有，但 chatter 的
  prompt_builder 会把它塞进 `values` 当随行元数据）→ 用它区分「现在构建的是哪个会话」；
- 让位行只写进 `stream:{stream_id}:{bucket}`，并且该流一旦不再让位就**主动删掉**，
  免得那句「我更想听你说」永远挂在那个会话上；
- 让位期间不再追加 `busy_suffix`（「手上正忙」和「这些先放一放」不能同时进上下文）；
- 拿不到 `stream_id`（老 chatter）或把 `scene.yield_stream_scope` 关掉时，退回旧行为：
  让位行合并进全局桶。

注入目标模板由 `plugin.target_prompts` 控制，默认同时兼容 `default_chatter_user_prompt` 与
`neo_default_chatter_user_prompt`，只有当前实际启用的 chatter 会真正命中。与 prompt_injector、
booku_memory 等注入器通过换行累加共存，互不覆盖。

## 让位

- 身份校验走权限系统（`generate_person_id` + `get_user_permission_level`），默认要求 `owner` 级
- `scene.yield_scope`：`all`（私聊 + 群聊都算）/ `private`（只认私聊）
- `scene.yield_stream_scope`（默认开）：让位**只在触发它的那个会话**生效；
  关掉则退回「让位心声替换场景行、写全局桶」的旧行为
- `scene.yield_idle_minutes`：让位持续的静默时长（默认 30 分钟）；设为 `0` 表示持续到当天结束
- 让位期间的重复开口不会改措辞、也不会重复记日志

## 离线生活（v1.1.0 起）

Bot 不在线的那段时间发生了什么，原本**没人知道**：重启之后它只觉得「刚才还在聊」。
装上 `time_sense` 之后，**每次启动都会自动做**这样一件事（不用去翻配置）：

```
time_sense 结算离线跨度（真的有多久）
        │
        ├─ 取日程表里与这段区间相交的条目（那段时间本来安排做什么）
        ├─ 取记忆插件里的相关事实（有则用）
        └─ 取前几天的日记（保持延续，别重复写已经写过的事）
                │
                ▼
        模型缝成 1-3 句第一人称的「随手记」
                │
                ▼
        落盘 diary-YYYY-MM-DD.json ──► 回喂进下一次日程生成的素材
```

几个刻意的设计：

- **检测机制**：`offline.enabled` 默认是 `false`（保守取值），但插件加载时会检测
  `time_sense` 在不在——**在位就自动打开**。自动开启只改**运行时**的配置值，不偷改你的
  `config.toml`；没装 `time_sense` 时它保持关闭，一次额外的模型调用都不会发生。
  想让离线生活**始终关闭**：`offline.enabled` 与 `offline.auto_enable_with_time_sense` 都设 `false`
- **它写的是记录，不是台词**：提示词明确要求「材料里没有的一律不写，宁可写得平淡」，
  并写明这段文字是给角色**当背景**的，不是让它照本宣科念出来
- **同一天只有一份日记**：一天里多次离线会合并进同一份，每个离线段落是一条 entry
- **写完还要被看见**：`offline.inject_enabled` 默认就是 `true`——日记只躺在盘上、
  主模型看不到的话，问「你昨晚干嘛了」照样现编，那就白写了。每轮都发，所以按
  `offline.inject_max_chars`（默认 600 字）截断；不想花这份 token 就关掉它
  或把 `inject_days` 设 0
- **三种情况不写**：开关没开、没有基线（首装）、短于 `offline.min_seconds`（默认 1800 秒）——
  几分钟的重启不值得写成故事
- **依赖是可选的**：`time_sense` 不在时 `wait_time_sense_settled()` 直接返回，安静跳过。
  两个插件的启动结算都是异步任务，所以日程这边会等 `time_sense` 的 `boot_at` 追上本进程
  启动时刻再动手，免得读到上一轮的旧跨度

## 存储

命名空间 `daily_schedule`，路径 `data/json_storage/daily_schedule/`：

- `schedule-YYYY-MM-DD.json`：某天的日程（条目、心声池、素材来源、模型标识；池子模式还带 `archetype` / `pool_id`）
- `log-YYYY-MM-DD.json`：某天的日志（生成记录 + 事件流，如让位）
- `persona-profile.json`：人设类型判定缓存（带人设指纹）
- `runtime-state.json`：让位与生成节流状态、最近一次失败原因
- `diary-YYYY-MM-DD.json`：离线生活日记（每个离线段落一条 entry，连带缝合时用到的锚点一起留档）
- `pool-current.json`：当前生效的日程池（日型 + 变体 + 心声 + 有效期）
- `pool-staging.json`：正在编的池子半成品（编好一个日型写一次，重启接着编；整池达标后删掉）
- `plan-year-YYYY.json` / `plan-month-YYYY-MM.json` / `plan-week-YYYY-Www.json`：三层规划（按时期各存一份，可回溯）
- `plan-pool-<层>.json` / `plan-pool-<层>-staging.json`：各层型池与半成品

三层规划为什么不只留"当前那一份"：生成下一期时要看**上一期实际怎么样**（以及随机评估的结果），
所以按时期存；`plan-pool-` 与 `pool-`（日程池）是两套，前者是年/月/周的模板，后者是每天日型的模板。

三个键族的分工别混：`schedule-` 是**计划**，`log-` 是**生成记录**，`diary-` 是**真的发生过什么**。
日记里连锚点一起存，是为了事后能核对「它这句到底是缝出来的，还是编出来的」。
池子单独两个键，是因为它跟"某一天"无关，而且"编到一半"必须和"正在用"分开存——
刷池失败时后者要原封不动。

## 测试

两个自检脚本在 `tests/`，用实例自带 venv 跑（别用系统 python）：

```powershell
$env:NEO_ROOT="F:\Neo-MoFox-Aemeath"
& "F:\Neo-MoFox-Aemeath\.venv\Scripts\python.exe" plugins\daily_schedule\tests\check_import.py
& "F:\Neo-MoFox-Aemeath\.venv\Scripts\python.exe" plugins\daily_schedule\tests\check_logic.py
```

- **`check_import.py`（41 项）**：**真实导入冒烟** —— 18 个模块逐个 import（「语法对」和
  「框架能加载」是两件事）、manifest 合法性与依赖声明、include 声明与文件对得上、配置关键默认值；
- **`check_logic.py`（108 项）**：逻辑自检 ——
  场景装配（让位行拆开 / 忙碌后缀抑制 / 闲时不附反应倾向）、
  **让位按流隔离**（本流拿到让位行、别的流只拿到场景行、认不出会话时退化为全局注入）、
  日记注入限次与字符闸、
  注入通道（`reminder_first` 不重复写、reminder 写失败必须退回 extra）、
  **日程池**（日型校验八种不合格、池子可用性、抽取确定性与 LRU、与前一天同段不重样、刷池失败不替换旧池）、
  **三层规划**（ISO 周期边界、规划校验、型池抽取 + 上层填充、随机评估收敛与幂等、链条生成）、
  **周程 → 日程**（标签命中优先，零额外调用）。

脚本都强制 `sys.stdout.reconfigure(encoding="utf-8")`：GBK 控制台下 print `✓`/`⚠` 会抛
`UnicodeEncodeError`，让「断言全过」变成 exit 1（踩过）。

样例人设使用中性的原创 OC 与虚构作品角色，不绑定任何具体作品。

v1.1.0 起另外覆盖：离线跨度与日程条目的相交取样、日记数据层（排序 / 条数上限 / 合并 / 脏数据）、
时间源在 `time_sense` 有和无两种情形下的取值与 `touch` 调用、启动落定等待（旧 `boot_at` 超时、
新 `boot_at` 通过、服务缺失返回假）、离线结算的四种分支（关闭 / 无基线 / 低于门槛 / 正常写），
以及 system reminder 的写读往返与「关掉 reminder 后仍走 extra」。

## 出问题时先看这几行日志

| 日志 | 含义 | 怎么办 |
| --- | --- | --- |
| `启动加载 · …` | 启动时查到了今天的日程 | 正常，紧跟着就是当天日程表格（当前时段带 `▶`） |
| `今天（X）还没有日程，将在 00:05 之后自动生成` | 启动时还没有日程 | 后面会跟一句排队/正在生成，生成完会再打一份 |
| `巡检 · X 日程正常（N 段）` | 巡检兜底跑过一次，一切正常 | 正常 |
| `日程生成失败：无法解析 JSON（N 字，内容：…）` | 模型没按格式返回 | 看括号里那段：结尾断在半句上就是被 `max_tokens` 截断，把 `model.max_tokens` 调大；是散文就换个更听话的模型或把 `model.model_name` 指到指定模型。完整原始返回留在 `data/json_storage/daily_schedule/raw-failure-last.json` |
| `日程生成失败：条目仅 N 条，低于下限` | 条目太少 | 把 `schedule.min_entries` 调小，或调大 `max_tokens` |
| `模型调用失败: … empty response` | 拿到空回复 | `actor` 任务里若混着**思考模型**，通常是思考链把 `max_tokens` 吃光了：调大到 8000 左右，或把 `model.model_name` 固定指到一个非思考模型 |
| 让位之后别的群也在「让位」 | 用的是旧版（全局桶） | v1.2.0 起让位走流私有 reminder，只对触发会话生效；确认 `scene.yield_stream_scope = true` 且 chatter 会把 `stream_id` 放进 `values` |
| 让位句一直挂在某个会话上 | 残留的流私有 reminder | 正常情况会在该流不再让位时自动删除；仍残留就用 `/日程 收回` 清一次让位状态，再让它构建一轮 prompt |
| `池子这一轮还没编够…保留旧池子，下轮接着编` | 某几个日型反复不合格（校验没过） | 看紧跟的 `日型 xxx 第 N 次生成不合格：…`：错在覆盖/衔接就换个更听话的模型（`model.model_name`），错在变体太少就调小 `pool.variants_per_slot` |
| `池子不可用，回退到 daily 模式生成今天` | 首次安装还没编完 / 池子过期 / 换人设 / 抽不出来 | 正常情况下一次刷池后自愈；持续出现就看 `/日程 池` 里的「最近失败」 |
| 连着几天像同一天 | 池子里日型太少、或退回了 daily | `/日程 池` 看日型个数：只有 1-2 套就把 `pool.archetypes` 调大（3-4）并 `/日程 刷池`；模式列显示「每日生成」说明在 daily 模式，把它改回 `pool` |
| `等 30s 仍没拿到日程服务，跳过启动日程报告` | 加载顺序异常或启动极慢 | 罕见；说明插件本身能用，只是这次没报备 |
| `人设判定失败，退回保守结果` | 人设判定那一步没解析出来 | 不影响生成，日程会按「原创 OC + 昵称」来做 |
| `模型调用失败: …` | 模型/网络层报错 | 按报错内容查模型配置 |
| 表格框线歪了 | 终端按字符宽度渲染，或窗口太窄折了行 | 表格按显示宽度（中文算两列）对齐，宽约 90 列；把终端拉宽到 100 列以上即可 |
| 文件里有 `启动加载 · …`，控制台却没有 | 报备打早了一点点，被启动进度条盖掉 | 1.0.0 起会等启动画面收尾再报；若仍看不到，看日志文件（控制台只是被覆盖，日志没丢） |

解析层本身已经比较宽容：代码围栏、前后散文、`//` 注释、尾逗号、全角引号、单引号、
JSON 前面带思考文字、甚至输出被 `max_tokens` 截断，都会尽量救回来（截断时至少保留写完的条目）。

想看完整的提示词与模型原始返回，把 `plugin.debug_log` 打开（DEBUG 级）。

## 维护者注意（七个踩过的坑）

1. **Service 不是单例**：`service_api.get_service()` 每次调用都会新建实例。
   跨调用者共享的状态只能放两处——类属性（进程内）或 `store`（落盘）。
   本插件的日程 / 日志 / 让位状态都在盘上，而「正在生成」闸门放在
   `ScheduleService._generating`（类属性）。放实例属性上等于没有闸门，
   同一天会被重复生成。
2. **`__init__.py` 不要 re-export 入口模块**：加载器是把入口文件当
   `daily_schedule.plugin` 直接执行的，那一刻包正在初始化中，
   再 `from .plugin import ...` 会循环导入并让整个插件加载失败
   （表现为 `cannot import name 'DailySchedulePlugin'`）。插件类从
   `plugin` 模块取用即可。
3. **画表格要自己算显示宽度**：框架日志先按 Rich markup 解析消息，再在终端里
   按列宽折行，所以中英混排必须按显示宽度补空格（中文两列，见 `table.py`），
   单元格里的 `[` 也要转义成 `\[`，否则会被当成样式标签吞掉。
   整行加粗只影响控制台——写进文件时框架会用 `Text.from_markup(...).plain` 把标记剥掉。
4. **启动期间的日志会被启动进度条盖掉**：Bot 初始化用 Rich `Live` 画进度条
   （`src/app/runtime/console_ui.py` 的 `startup_progress`），`Console.print` 并不与
   `Live` 协调，这期间打的日志会被每秒十几次的进度重绘覆盖——**文件日志照写，控制台看不见**。
   所以「启动后要给人看的东西」必须等启动画面收尾：本插件用「调度器已启动」
   （`Bot.start()` 里 `scheduler.start()` 之后）作为信号，并且超时就照打不误。
5. **`on_prompt_build` 的参数里没有 `stream_id`，但 `values` 里有**：
   `params` 只有 `name` / `template` / `values` / `policies` / `strict`，看着像「拿不到是哪个流」，
   于是很容易顺手写成全局 bucket（v1.1.1 就这么错了）。实际上 chatter 的 prompt_builder 会把
   `stream_id` 塞进 `values` 当**随行元数据**（不在模板占位符里，所以不会渲染出来，但事件里能读）。
   要按流注入就走 `prompt_api.add_stream_reminder` / `delete_stream_reminder`——
   框架已经按 `stream:{id}:{bucket}` 约定好了，chatter 建请求时全局桶与当前流私有桶**一起拾取**。
   教训：判断「某个参数拿不到」之前，先把它整份打印出来看看。
6. **回喂给模型的东西，措辞就是它的行为指令**：`_history_block` 早年写的是
   「让今天和它自然接得上」，结果模型三天抄出同一套骨架（连细节都在重复）；
   改成「这些是**已经用过的**安排，今天的场地与事件至少一半要换」之后才谈得上变化。
   池子把这层从"每天赌模型听话"变成了结构保证：**变化来自轮换，连续性来自事实**。
   写提示词时记住：模型不会读你的意图，只会读你给的字面要求。
7. **抽取必须可复现**：种子用 `hashlib`，别用内置 `hash()`——后者带进程随机化，
   同一个日期在两次启动里会抽出不同的日程，那意味着"她今天在做什么"会随重启改变，
   日记与日程也就对不上了。
